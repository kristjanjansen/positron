## 1. The one design rule that made this cheap

**Every touch affordance is inside `@media (pointer: coarse)`, and every
capability question is asked LIVE.**

`pointer: coarse` — not a viewport width — is the correct test. A 1024 px
tablet has fingers; a 700 px desktop window does not. Because a mouse never
matches the block, the existing headless verifies (which run `pointer: fine`)
are unaffected *by construction* rather than by measurement, which is why four
regression gates came back byte-identical on the first try.

"Live" matters as much as "coarse". Two bugs came from
`const COARSE = matchMedia(...).matches` read once at boot:

* `proto/megatimeline` rendered its desktop panel because the harness applies
  device emulation *after* navigation, so the boot-time read was `false`;
* `proto/remixer` rendered every year-strip mark as an individual control for
  the same reason.

The megatimeline fix is a `change` listener that re-applies; the remixer fix is
better — **move the decision into CSS** (`.it { pointer-events: none }` under
the media query) and read `matchMedia(...).matches` at the call site. A media
query is live by definition; a boolean captured at boot is wrong on exactly the
devices it is for.

## 2. `timeline/strip.mjs` — touch in the shared component

### `touch-action` discipline

```
canvas.style.touchAction = opts.touchAction || 'pan-y';
```

That declaration IS the contract: **the strip owns the horizontal axis and the
pinch; the page keeps the vertical one.** A vertical swipe scrolls the page and
the browser hands us a `pointercancel`, which is the right outcome and costs no
code. Nothing in the component calls `preventDefault` on a touch stream, so the
listeners never fight the compositor.

The previous value was `touch-action: none`, which is correct only for a
surface that fills the viewport and has no page scroll to protect —
`proto/megatimeline`'s `#stage` keeps it for exactly that reason, and says so
in a comment. A client that is full-screen passes `touchAction: 'none'`.

### The gesture machine

A finger is not "a mouse, fatter", and three differences drive the whole design:

1. **A mouse has a resting position; a finger does not.** Press *is* first
   contact, so the desktop press-to-seek would make every touch a destructive
   seek before the user had said what they wanted. Touch therefore **defers**:
   the gesture is `undecided` until it passes the 10 px tap slop or the finger
   lifts. Drag ⇒ pan. Lift-without-drag ⇒ tap ⇒ seek.
2. **There is no wheel**, so zoom is pinch, about the **midpoint** — the same
   invariant `zoomAt()` already keeps for a cursor, written for two moving
   anchors instead of one fixed one. Measured drift of the time under the
   midpoint across a ×3.33 zoom: **0.00 px**.
3. **There is no hover**, so the tooltip needs a tap equivalent, and it must be
   **sticky** (a finger covers the thing it is describing). `pointerleave` is
   ignored for touch pointers — for touch it fires the instant the finger
   lifts, which erased the tap tooltip one frame after it appeared.

The playhead is the one exception to "drag = pan": it is a 1.5 px line, so a
press within `touchSlop` (22 px) of it **scrubs**. Desktop keeps its 1 px
precision because that branch is only reachable from a touch pointer.

### Finger slop without touching desktop precision

`hitTest(px, py, tolPx = 6)` — the hit *geometry* is identical on both inputs,
only the radius differs (6 px mouse, 22 px finger). Desktop precision is
therefore unchanged by definition, not by test.

### Other strip changes

* **Narrow-viewport gutter**: below 520 px the 92 px label column is clamped to
  46 px. It is the one piece of chrome that can shrink without moving a
  measured number, because `plotW()` is derived from it and every renderer
  already draws in plot space.
* **`globalThis.__strips`**: a live registry, spliced on `dispose()`. Without
  it a harness cannot reach a strip that a client keeps in a module closure
  (`proto/paths` does), and adding a global to every client is five edits to
  files this component does not own.
* **`gesture()` / `hover()`** on the returned API — the only way a headless
  harness can tell a pan from a pinch from a tap without reading pixels.
* **`gesturestart`/`gesturechange` preventDefault** — iOS Safari still ships
  its own pinch alongside the standard pointer stream; without this the page
  zooms and our pinch never gets its second pointer.

## 3. iOS gotchas, and what each one cost

| Gotcha | Where it bites | Handling |
|---|---|---|
| No viewport meta ⇒ 980 px layout, scaled down | megatimeline, remixer, kurenniemi (replay too) | `width=device-width, initial-scale=1, viewport-fit=cover`. This alone was the single biggest bug on three of the four public surfaces. |
| `100vh` > visible viewport with the URL bar showing | megatimeline `#stage` | `100dvh`, plus `visualViewport` `resize`/`scroll` listeners — iOS changes the visible viewport **without firing `resize`** when the URL bar slides away, so an `inset:0` canvas kept its old height. |
| AudioContext starts **suspended** | remixer | Unlock on the first gesture of any kind (`pointerdown`/`touchend`/`keydown`, captured), plus a full-screen tap-to-start panel if `resume()` still fails. |
| `play()` refused outside a gesture — *and the rack's plays happen after an `await`* | remixer | The async play is the real problem: a finger started it, but it is not "inside" the gesture any more. Fix is **priming** — play+pause every media element with a silent WAV during the first real gesture, which marks each element user-activated for the session. |
| `au.play().catch(() => {})` | kurenniemi | Was swallowing the refusal and leaving a dead `<audio>` under a provenance card claiming a tape was mastering the deck. Now the refusal surfaces as one obvious button naming the tape. |
| Autoplay refused | replay | `vid.play()` failure reveals a tap-to-start overlay; it is `display:none` unless play actually rejects, so the measured gate never sees it. Sound is a **second, separate** button, because unmuting outside a gesture is silently refused. |
| `playsinline` mandatory | replay | Already present; `webkit-playsinline` and `disablepictureinpicture` added. Without it iOS tears the video into the system player and the overlay, the subtitle styling and the burned-row decode all go with it. |
| **No classic `MediaSource` on iPhone** | replay, remixer | See below. |
| iOS zooms the page in on focusing an input under 16 px, and never zooms back | studio/console | `font-size: 16px` on `select`/`input[type=text]` under coarse. |
| 300 ms double-tap delay | all | `touch-action: manipulation` on buttons. |

### MediaSource, said out loud

hls.js is Media Source Extensions and nothing else. An iPhone has **no classic
`MediaSource` at any iOS version**; 17.1+ added `ManagedMediaSource`, a
different constructor with a different contract. So the "unsupported" branch is
not an edge case on a phone — it is *the* case.

* **`proto/replay/replay.html`** used to `reject("hls.js unsupported")` there,
  which meant `phase=failed` and a black rectangle. It now falls back to
  **native HLS** (`vid.src = SRC`) and reports which path it took in
  `S.mediaPath` / `S.media` and what that costs in `S.degraded`, both in the
  HUD. What is genuinely lost is on the record: no rendition lock (the burned
  rows are calibrated at 720p, so the **content** anchor cannot form — use
  `anchor=stamp`), and a cross-origin native-HLS video **taints the canvas** on
  Safari, so `getImageData()` in `decodeAt()` throws and the burned-row
  cross-check is unavailable on iOS at all, with or without a rendition lock.
* **`proto/remixer/index.html`** already had the correct degradation
  (`else L.el.src = src.url`). What was missing was **saying so**: a silent
  fallback and a silent failure look identical. `#compat` now names it —
  playback works, per-layer buffer statistics and the rendition lock do not.
* The CDN failing to load is a *different* failure from MSE being absent, and
  on a phone the first is common (captive portal, content blocker). Both are
  now distinguished and both fall back.

## 4. Marks are not controls

Three surfaces had the same problem: a timeline mark is 2–9 px wide, and there
is no world in which every mark becomes a 44 px control — they would all
overlap. Growing them is the wrong answer twice over.

The right answer, applied identically in three places: **the mark stays a mark
(`pointer-events: none` under coarse) and the container gets one delegated
hit-test with a finger radius**, picking the nearest item within ~20 px.

* `proto/remixer` `#strip` — year marks, 22 px slop
* `proto/kurenniemi` `#axis` — item bars, 20 px slop, and it arbitrates between
  "focus this item" and "seek to this instant" by distance
* `proto/megatimeline` `#stage` — canvas `hitRects` grown by 12 px

This is the same answer `timeline/strip.mjs` gives for a canvas tick, so the
four surfaces now agree on what a tap near a mark means.

## 5. Hover has a tap equivalent everywhere

`proto/megatimeline`'s hover card was **unreachable on a phone** — a finger
cannot dwell, so the 600 ms dwell-gated content fetch never ran — and the only
thing a tap *did* do was open a new tab, which is the most destructive of the
two outcomes and the one a mis-aimed finger produces most often. On coarse
pointers the first tap now shows the card (running the same gated fetch
immediately, since a tap *is* the intent the dwell stood in for) and OPEN is a
real 44 px button inside it. Double-tap-to-dive on the ruler is owned
explicitly rather than left to Chrome's synthesized `dblclick`, which it
declines to emit exactly when `touch-action: none` is in play.

## 6. The harness, and three bugs that read as product bugs

`timeline/lab/mobile-verify.mjs`, `timeline/lab/strip-touch.html` (a bench for
the shared component — see §7), `timeline/lab/cdp-ev.mjs`.

Devices: iPhone-class 390x844 @3x and small-Android 360x800 @2x, both
orientations. `mobile: true` is what flips `pointer: coarse` / `hover: none`
and the visual-viewport model; a width override alone does none of that, which
is why a resized window is not a test.

Three harness bugs each produced "touch does nothing", which is
indistinguishable from a broken surface until you ask the page directly:

1. **`touchEnd` must carry no touch points.** CDP's contract is explicit, and a
   `touchEnd` carrying one is silently dropped — leaving that pointer id *live*
   in the page's pointer map, so the next one-finger drag arrives as
   `pointers.size === 2` and is read as a pinch with a stale anchor.
2. **Chrome's input router is per render widget and does not reliably follow a
   same-tab navigation.** After a gesture battery on surface A,
   `Input.dispatchTouchEvent` on surface B is accepted, acknowledged, and
   delivered *nowhere* — the page's own `pointerdown` listener counts zero.
   `about:blank` in between is not enough. **One tab per surface** is. There is
   an assert for this now (`M2c stage-receives-touch`) so it can never be
   mistaken for a product bug again.
3. **Dispatching before the page's own fit.** megatimeline's census finishes
   with `fitX()`, which overwrites `panX`/`zx` wholesale; a gesture sent before
   that is real, lands correctly, and is then erased. The harness waits for
   `window.__mt.ready`, it does not sleep and hope.

Two assertion definitions were also wrong at first and are worth keeping right:

* **Overflow**: an element sticking out to the right is only a bug if nothing
  between it and the root clips it. A ruler tick at x=1200 inside an
  `overflow: hidden` ruler is correct rendering, and flagging it hides the real
  ones.
* **Tap target**: the target is the thing a finger *activates*, not the thing
  it can see. A 22 px checkbox inside a 44 px row that toggles it, or one whose
  `<label for=…>` is 44 px tall, **is** a 44 px target — and a rule that cannot
  say so forces controls to be uglier than they need to be.

## 7. `proto/paths` — the strip's own host page is the blocker

`proto/paths/paths.js` is the richest client of `timeline/strip.mjs`, and it is
owned by another machine. Its page CSS **lays the strip canvas out at 2 px wide
at a 390 px viewport** (the whole page is `doc 485 / client 390`), so the
component cannot be exercised there at all — every gesture assert reads as a
silent failure. The harness now diagnoses this explicitly rather than reporting
a component fault:

```
FAIL paths/iphone-390x844@3 strip-canvas-has-width —
  host page laid the canvas out at 2 px wide at 390 px viewport
```

That is why `timeline/lab/strip-touch.html` exists: a bench that mounts the
shared component on a page which also has real vertical page scroll to fight
over, so `touch-action: pan-y` is a claim with something to test it against.
**`proto/paths/paths.html`'s layout is the open item for its owner** — one
`max-width: 100%` on the strip container is likely all it needs, after which
the same 10-assert battery should pass there unchanged.

## 9. What still will not work on a real phone — emulation cannot tell us

Everything above is Chrome-on-macOS pretending. These are the things that
require a real device, in rough order of how likely they are to bite:

1. **Safari is not emulated at all.** CDP emulation gives us Blink with a small
   viewport and a coarse pointer. Every WebKit-specific behaviour is untested:
   `touch-action` coverage of pinch, whether `gesturestart` still fires
   alongside pointer events, `dvh` behaviour during the URL-bar transition (as
   opposed to its final states), and Safari's own double-tap-to-zoom heuristics
   fighting our double-tap-to-dive.
2. **The audio unlock is asserted nowhere.** Headless Chrome runs with
   `--autoplay-policy=no-user-gesture-required`, so the unlock path is *dead
   code in the harness*. The AudioContext-suspended branch, the element
   priming, and both tap-to-start panels have been reasoned about and written
   but **never executed under a real refusal**. This is the single largest
   untested surface in this work.
3. **The burned-row decode on iOS is expected to be impossible**, not merely
   degraded — cross-origin native HLS taints the canvas. `replay.html` now says
   so, but nobody has watched it say so on a phone.
4. **iOS Low Power Mode / Silent Mode / "Auto-Play: Never"** each refuse
   differently, and the tap-to-start copy guesses at which. The `err.name` is
   surfaced so the guess can be corrected from a real failure.
5. **Managed MediaSource is untested.** We detect it and report it; we have
   never run against it. Whether recent hls.js drives it, and whether it would
   be better than the native path, is unknown.
6. **Real touch physics.** `Input.dispatchTouchEvent` produces clean synthetic
   points at 12 ms intervals with a fixed 12 px radius. A real finger has
   contact-patch drift, palm rejection, variable pressure, and a rolling
   release that can move 5–10 px after the user believes they have lifted. The
   10 px tap slop and 400 ms tap window are guesses calibrated against
   synthetic input; they will need adjusting.
7. **No inertia / rubber-banding anywhere.** The strip's pan stops dead when
   the finger lifts. megatimeline has inertia (inherited from the EKA lineage);
   the strip does not, and on a real phone that will feel broken next to every
   other scrollable thing on the device.
8. **Performance is unmeasured on real silicon.** The strip caps DPR at 2 while
   a 390x844 @3x iPhone wants 3, and megatimeline mounts up to 300 DOM cards.
   Headless Chrome on a Mac says nothing about thermal throttling, a 60 Hz
   compositor under memory pressure, or how a 4-year-old Android handles the
   canvas repaint.
9. **Network.** Every measurement here is over localhost or a warm R2 edge. The
   replay's 22 s settle, the megatimeline census, and the remixer's chord all
   assume bandwidth a phone on cellular does not have.
10. **Landscape safe areas and the home indicator.** `env(safe-area-inset-*)`
    is declared everywhere it should be, but headless Chrome reports all four
    insets as 0, so **none of that CSS has ever produced a non-zero value**.
11. **The on-screen keyboard.** `studio/console.html`'s cue box and the
    remixer's year inputs will be covered by it, and `visualViewport` scrolling
    on focus is untested.
12. **Rotation mid-gesture** — the harness sets an orientation and then
    gestures; it never rotates with a finger down.
