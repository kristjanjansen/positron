# WebMCP, and whether positron should use it

Researched 2026-10-14 for the owner's *"Investigate webmcp, could we use it.
Research."* Every source below was read on 2026-10-14. Three kinds of claim are
marked:

- **MEASURED**: run on this machine on 2026-10-14 (Google Chrome
  155.0.8059.40, headless, through `demo/chrome.mjs`; scripts in the session
  scratchpad, nothing in the site changed).
- **DOCS**: read in a primary source that day (the spec, its repository, Chrome
  docs, the npm registry, a GitHub issue).
- **INFERENCE**: reasoned, not read and not run.

## 0. The answer first

**Yes, as a small experiment on /connect/ only, and not yet as a shell-wide
feature.** WebMCP is real and runs in the Chrome on this desk behind a flag,
the API is small, and /connect/ already has the one property that makes it
safe: `bay.link` refuses a link out of somebody else's server unless a person's
own press gave `consent: true`, and a tool call is never that press. What does
not exist yet is an audience: no mainstream agent a visitor already has calls
these tools by itself today (section 1.4). So the first step is cheap, local
and for us: five tools on /connect/, feature detected, no polyfill, no origin
trial token, and a harness check that calls them over CDP.

## 1. What WebMCP is today

### 1.1 Status and who is behind it (DOCS)

- **A Draft Community Group Report of the W3C Web Machine Learning Community
  Group, dated 13 October 2026.** It is not a W3C Standard and not on the
  Standards Track. Editors: Brandon Walderman (Microsoft), Khushal Sagar and
  Dominic Farolino (Google). [spec]
- The brief was right on all four counts (Web ML CG, Microsoft and Google,
  `modelContext`, a Chrome preview and origin trial) and **wrong on one name**:
  it is no longer `navigator.modelContext`.
- **The API moved from `navigator.modelContext` to `document.modelContext`.**
  The proposal began as `window.agent`, shipped in Chrome 146 behind a flag as
  `navigator.modelContext`, the July 2026 draft moved it to `document`, and
  Chromium removed `navigator.modelContext` and `navigator.modelContextTesting`
  in Canary 152.0.7946.0 (8 July 2026). [mcp-b-270], [studiomeyer]
  MEASURED below: in Chrome 155, `navigator.modelContext` is `undefined` and
  `document.modelContext` is an object.
- **The declarative form API is not in the spec.** The explainer calls it
  *"being explored separately ... not part of the specification at this
  time"*. [explainer] Chrome implements it anyway (MEASURED, 1.3).

### 1.2 The API shape (DOCS, the spec's IDL)

```webidl
[Exposed=Window, SecureContext]
interface ModelContext : EventTarget {
  Promise<undefined> registerTool(ModelContextTool tool, optional ModelContextRegisterToolOptions options);
  Promise<sequence<RegisteredTool>> getTools(optional ModelContextGetToolOptions options);
  Promise<DOMString> executeTool(RegisteredTool tool, optional object inputObject, optional ModelContextExecuteToolOptions options);
  attribute EventHandler ontoolchange;
  attribute EventHandler ontoolactivated;
  attribute EventHandler ontoolcancel;
};
```

- **A tool** is `{ name, description, execute, title?, inputSchema?,
  annotations? }`. `name` is 1 to 128 characters of letters, digits, `_`, `-`
  and `.`; an empty name or description, an invalid schema or a duplicate
  name is an `InvalidStateError`.
- **`inputSchema` is JSON Schema.** `execute(input, { signal })` returns a
  promise of anything; the result reaches the agent serialised as a JSON
  string.
- **There is no `unregisterTool`.** Registration takes `{ signal }` and
  aborting that `AbortSignal` unregisters the tool. `exposedTo` (a list of
  origins) lets a cross-origin frame see it.
- **Annotations are hints, all `false` by default**: `readOnlyHint`,
  `untrustedContentHint` (*"output contains untrusted data"*),
  `consequentialHint` (*"significant, real-world, or non-reversible"*) and
  `debugging`.
- **`getTools()` and `executeTool()` are for in-page agents** written in
  JavaScript, possibly in an iframe. The browser's own agent and extensions
  reach tools by a separate internal route (in Chrome, a CDP domain, 1.3).
- **A permissions policy feature `tools`**, default allowlist `self`, so a
  cross-origin iframe cannot register or call unless allowed.

### 1.3 What Chrome 155 on this desk actually does (MEASURED)

A page served over `http://127.0.0.1` (a secure context) registered one
imperative tool `add` and carried one annotated `<form toolname=...>`. Five
launches, one per flag set:

| launch flags | `document.modelContext` | `navigator.modelContext` | registered | tools seen by `getTools()` | `executeTool(add, {a:2,b:3})` |
| --- | --- | --- | --- | --- | --- |
| none | `undefined` | `undefined` | no | | |
| `--enable-features=WebMCP` | object | `undefined` | yes | `add`, `say_hello` | `"{\"sum\":5}"` |
| `--enable-features=WebMCPTesting` | object | `undefined` | yes | `add`, `say_hello` | `"{\"sum\":5}"` |
| `--enable-experimental-web-platform-features` | object | `undefined` | yes | `add`, `say_hello` | `"{\"sum\":5}"` |

- **Off by default in Chrome 155 stable**, and any of the three switches turns
  it on. `chrome://flags/#enable-webmcp-testing` is the documented switch for
  a person. [chrome-docs]
- **The declarative form becomes a tool natively**: `<form toolname="say_hello"
  tooldescription="..."><input name="who" toolparamdescription="...">`
  arrived as a tool with schema `{who: string}`, without any polyfill.
- **There is a CDP domain, `WebMCP`, marked experimental, present even with the
  feature off** (it then simply reports no tools). Commands `enable`,
  `disable`, `invokeTool(frameId, toolName, input)` answering an
  `invocationId`, `cancelInvocation`; events `toolsAdded`, `toolsRemoved`,
  `toolInvoked`, `toolResponded(invocationId, status, output, errorText,
  exception)` with status `Completed`, `Canceled` or `Error`.
- **`WebMCP.enable` replays every registered tool** as one `toolsAdded`, with
  the annotations renamed (`readOnly`, `untrustedContent`, `consequential`,
  `autosubmit`) and a stack trace of the `registerTool` call.
- **`invokeTool` round trips**: `add` completed with `{sum: 5}`; a tool that
  throws came back `status: Error` with the exception's message (`Error:
  refused: ports do not fit`); an unknown name is a CDP error `-32602 Tool not
  found`. The declarative form, with no `toolautosubmit`, produced no response
  in 1.5 s and no submit event: it fills the fields and waits for a person,
  which matches the polyfill's documentation. [npm-polyfill]
- 🔴 **A tool call carries NO user activation.** Inside `execute`,
  `navigator.userActivation.isActive` and `hasBeenActive` both read `false`.
  So anything the page gates on a gesture stays gated. The same probe's
  `AudioContext` reached `running` anyway, but that was headless Chrome, whose
  autoplay policy is not a visitor's; **whether a real Chrome lets a tool start
  sound is NOT measured** and should be assumed no.

yet.

### 1.5 Security and consent (DOCS)

- **The spec's security section names five risks**: prompt injection through
  tool metadata or outputs, misrepresented intent, privacy leakage through
  over-parameterised tools, same-origin boundary violations, and private
  browsing. Its mitigations are the `tools` permissions policy, input length
  limits, shared attack datasets and the `untrustedContentHint`. [spec]
- **The spec defines no consent step.** Nothing in it makes a browser ask a
  person before a tool runs; `grep requestUserInteraction` over the spec source
  (`index.bs`, 1,977 lines, fetched 2026-10-14) finds nothing. Chrome's
  security guide (updated 1 September 2026) says a draft
  `requestUserInteraction()` *"remains under development"*, and that with
  `consequentialHint: true` *"the agent or browser can request user
  confirmation"*. **Can, not will.** [chrome-secure]
- **The page cannot tell who is calling.** A tool sees an input object and an
  abort signal; there is no agent identity and no user gesture (MEASURED
  1.3). **INFERENCE: every guard has to live in `execute`, and a page must
  treat a tool call exactly as it treats a synthetic click**, which positron
  already does with `isTrusted`.

### 1.6 How it relates to MCP proper (DOCS)

- **WebMCP is not an MCP server.** There is no JSON-RPC, no transport and no
  session: a page hands the browser JavaScript functions with MCP-shaped
  metadata (name, description, JSON Schema, annotations), and whatever agent
  the browser lets in calls them in that tab. The tools live as long as the
  page does.
- **Bridges turn it back into MCP.** Chrome DevTools MCP exposes a tab's
  WebMCP tools as two MCP tools over CDP [devtools-mcp]; community bridge
  extensions forward them over a WebSocket to a local MCP server for Claude
  Code. [mcpcat]
- **mcp-b**: `@mcp-b/webmcp-polyfill` 6.0.2 (published 2026-10-13) is a
  *"temporary compatibility distribution"* of the CG's own polyfill. It
  installs `document.modelContext` only where the browser has none, preserves
  a native one, does **not** provide the old `navigator` alias, and adds a
  declarative form layer. `@mcp-b/global` adds MCP transports, and
  `@mcp-b/transports` carries postMessage, extension and iframe channels.
  [npm-polyfill] (read off the npm registry with `npm view`.)
- **INFERENCE: the polyfill only helps a visitor who also runs an MCP-B
  extension or an in-page agent**, because a polyfilled `document.modelContext`
  has no browser agent behind it. For positron's audience that is nobody, and
  loading it from unpkg would be a third-party fetch on every visit.

## 2. Fit with positron

### 2.1 /connect/ (http://127.0.0.1:8890/connect/, `demo/connect/index.html`)

**A correction to the brief first. /connect/ spends nothing on the wish worker
today.** The typed request was taken out on 2026-10-14 (*"rm ask button and
input atm"*, line 282); `ask()` is called only from the self-check (line 760),
and there `post()` answers from `EXAMPLES` or `CANNED` without a fetch. So
WebMCP would not take a bill to zero on /connect/; it would bring back natural
language without bringing the bill back. The worker's other callers are
/wish/ and `room/words` (`grep wish.positron.studio`).

**What already makes it safe** (read in the page and `bay.mjs`):

- `connect(from, to, transforms, consent)` passes `consent` straight to
  `bay.link`, and the page sets it from `e.isTrusted === true`.
- `bay.validate` refuses a link out of a node with `consent` (every
  `external` node, `err:station`) unless `opts.consent === true`, `=== true`
  and nothing looser (`bay.mjs` around line 1093).
- So a tool that calls `connect(..., false)` **cannot** open ERR's station, by
  the same rule that stops a harness. Nothing new has to be written for it.
- Listening in a room (`listen`) joins a relay room, and `studio-1` is refused
  without a trusted press; it simply does not get a tool.
- Sound starts on *"the first press on a face (decision D4)"*: `rt-keys.mjs`
  calls `wake()` from the keyboard's own pointer handler, so a tool can put a
  note on a link but cannot start the sound device. That is the project's
  rule, and it holds for an agent because a tool has no user activation
  (MEASURED).

**The tools, each mapped to code that exists:**

| tool | hints | does | maps to |
| --- | --- | --- | --- |
| `list_nodes` | readOnly | nodes and their ports, optionally filtered by `site` (`web`, `pi-1`, `cf-*`, `err`) or `medium` | `bay.nodes()`, `bay.ports()`, the page's `groupOf`, `typeOf` and `PAGES` (which concept page builds each node) |
| `list_links` | readOnly | what is linked now, printed, with ids | `bay.links()`, `printLink` |
| `list_examples` | readOnly | the 20 example sentences and the page each comes from | `EXAMPLES` (`say`, `page`) |
| `link` | none | link `from` to `to` with optional MIDI transforms; answers `{ ok, id, why, fix }` | `checkTransforms`, then the page's `connect(from, to, transforms, false)`, which expands the knob type with `knobLinks`, calls `bay.link` and redraws |
| `unlink` | none | take a link away by id | `removeLink(id)` |
| `build_example` | none | replace the patch with one example's links | `build(ex, false)`; the radio key example is refused at its ERR hop, by design, and the answer says so |
| `play_note` | none | send note on and off on `web:keys:midi-out`; answers how many the synth heard and whether sound is running | `bay.send` on the keys' port, `runtime.get('web:synth').heard()`, `runtime.context()?.state`; **never `wake()`**, so until a person has pressed a key it answers *"the sound starts on your first press on the keyboard"* |
| `set_knob` | none | set one synth parameter by name and value | `runtime.get('web:knob-<param>').knob.set(knobRaw(param, value))`, `PARAM_NAMES` for the enum; refused when that knob is not linked |

- **Five of these are enough for a first step** (`list_nodes`, `list_links`,
  `list_examples`, `link`, `unlink`). `build_example` is one line on top.
  `play_note` and `set_knob` wait for the D4 question below.
- **Every refusal is returned, not thrown away.** `bay.link` already writes a
  `why` and a `fix` in words; returning them is what lets an agent correct
  itself, which is what the CG's best practices ask for (*"return clear,
  actionable error messages so the agent can self-correct"*). [explainer]
- **The picture follows by itself**, because the tools call the same
  `connect`/`removeLink` a press calls, and both end in `redraw()`. *"Synchronize
  visual UI state"* is the CG's own rule and the page already obeys it.
- **The size matters**: the bay holds about 190 ports (the self-check prints the
  count) and the wish worker was capped at 64 for a model's sake. **INFERENCE:
  `list_nodes` should return nodes with their port names, filterable, not all
  ports flat**, because the tool budget is the visitor's model's context.
- **Open question for the owner, D4 and agents.** Should an agent be able to
  make sound at all? The rule today is *"on the first press on a face"*. An
  agent tool that waits for that press keeps the rule; one that calls `wake()`
  breaks it. This research recommends keeping it.

### 2.2 Concept pages generally, from `demo/shell/shell.mjs`

**Not from `mount()`, and not one generic tool set.** Read in the tree:

- `mount()` never sees a bay. 40 concept pages call `createBay()` and only 6
  publish it on `window.__demo.bay` (`room/words`, `radio/tuner`, `code/piano`,
  `synth/dots`, `remote/circuit`, `remote/piano`). A shell-level tool would
  have nothing to link with on 34 pages.
- **A generic "press a control" tool is the dangerous one.** Many pages start
  something on a press: join a relay room, start a camera, publish to Stream,
  reach the Pi. A tool's press is a synthetic click (`isTrusted` false), and
  only the pages that test `isTrusted` would refuse it. **INFERENCE: one
  generic press tool would turn every page that forgot that test into a way
  for an agent to start a paid or remote thing.** That is the opposite of the
  rule in `bay.mjs`, where the consent is a property of the node so no page can
  forget it.
- **What could be generic, later**: a helper `demo/shell/webmcp.mjs` exporting
  `registerPageTools({ bay, d, extra })`, opted into per page with one line,
  registering `read_readout` (`__demo.readout`), `list_links`, `list_ports`,
  and `link`/`unlink` with `consent: false` hard-coded. The page lists its own
  `extra` tools. One shared file, written once by one agent, as the CLAUDE.md
  stream rule asks.
- **The project rules hold** if it is done that way:
  - *A self-check never runs for a visitor.* Registering a tool is not a check
    and runs nothing; the checks that CALL the tools run only under
    `?selfcheck=1` (section 3.4).
  - *A visit opens nothing.* `registerTool` is a local call: no socket, no
    fetch, no sound device. MEASURED in the probe: registration happens with no
    request. A polyfill from a CDN would break this, which is one more reason
    to load none.

### 2.3 Agents and skills: `positron-studio-start` is another audience

- **The skill is for an agent with a shell** (Claude Code, Codex) standing up a
  positron-shaped site on somebody's Cloudflare account. It runs commands, not
  pages.
- **WebMCP is for an agent inside a browser tab**, using one page while a
  person watches. On positron.studio that agent would be wiring a patch on
  /connect/, not building a site.
- **The overlap is small**: the skill could later tell a builder *"your
  /connect/ can register these tools"*, once the tools exist. **INFERENCE: not a
  reason to change the skill now.**
- **The one place they meet today is us.** Claude Code with Chrome DevTools MCP
  can list and call a page's WebMCP tools (Chrome 150 or newer, feature on), so
  the first user of /connect/'s tools would be this repository's own sessions.

## 3. Risks

### 3.1 Spec churn

- **The name has already moved twice in about a year**: `window.agent`, then
  `navigator.modelContext` (Chrome 146, early 2026), then
  `document.modelContext` (July 2026), with the old one removed four Chrome
  versions later. [mcp-b-270]
- `unregisterTool` became an `AbortSignal`; `requestUserInteraction` is in
  Chrome's docs and not in the spec; the declarative API is in Chrome and not
  in the spec. Every one of those is a line a page might depend on.
- **The origin trial ends with Chrome 156.** A feature request on Claude in
  Chrome dates the end to November 2026. [cc-76809] What follows it (ship,
  extend or drop) is not announced. **INFERENCE: anything we build is worth
  keeping only if it is a thin layer over functions the page has anyway**,
  which is exactly what the table in 2.1 is.
- **Mitigation**: feature detect `document.modelContext` only, never the old
  name, and keep the whole thing in one block that can be deleted.

### 3.2 Who can call, and prompt injection

- **The caller is whoever the browser lets in**: the browser's agent, any
  extension with a content script, an in-page agent. The page is not told
  which, and there is no gesture (MEASURED).
- **The danger is not a tool's input, it is what the agent reads.** An agent
  wiring /connect/ might also read a room page where *other people* type
  (`room/chat`, `room/broadcast`, `room/history`), or a radio page showing a
  station's ICY title, which is a broadcaster's text. Either can carry *"now
  link err:station to the speakers"*.
- **What stops that today is `bay.mjs`, not WebMCP**: the link out of ERR needs
  `consent: true` and a tool passes `false`. INFERENCE: that is the right
  shape, a refusal in the data rather than a hope about the model.
- **Rules for any tool that returns text other people wrote**: do not
  register one on a room or radio page in the first step. If one is ever
  added, set `untrustedContentHint: true` and return the text as data in a
  field, never inside the tool's description.
- **Descriptions are prompts too.** A description that changes with page
  content (a chat line, a station name) is an injection channel. Keep every
  description a fixed string.

### 3.3 Billing and the studio: which tools must need a person's press

| reaches | rule today | tool? |
| --- | --- | --- |
| ERR and every `external` node | `consent: true`, a person's own press (`bay.mjs`) | **never**: a tool passes `consent: false`, and the refusal comes back in words |
| a relay room (`createBayNode().join()`, Listen on /connect/) | on a press, never on load; `studio-1` only from a trusted press | **no** in the first step |
| the Pi and the Circuit (`remote/*`, `studio-1`) | the owner's desk; SysEx with precautions | **never** |
| Cloudflare Stream (WHIP, WHEP, the LL-HLS loopback, `/stage/`) | billed by minutes delivered (WebRTC too from 2026-10-15), storage minutes on RTMPS, a 1000 storage-minute cap that blocks new streams | **never** |
| the wish worker (Workers AI) | a person's press | **no**: the point of WebMCP here is that the visitor's agent does the language |
| R2 reads (`recording`, sample banks) | on a press with the engine that plays them | later, and only as a read a person started |
| the sound device | the first press on a face (D4) | a tool may send MIDI; it may not `wake()` |
| linking two in-tab nodes | free, local | **yes** |

**The general rule this suggests (INFERENCE):** a tool may do what costs
nothing and leaves the tab; anything that opens a connection, reaches the
studio, or spends money stays behind a press, and the refusal says so in the
tool's answer.

### 3.4 Testing headless

- **It works in our own harness Chrome, MEASURED.** Two routes, both run
  2026-10-14 on Chrome 155:
  1. **In the page, under `?selfcheck=1`**: `document.modelContext.getTools()`
     then `executeTool(tool, input)`, which returns the JSON string. This fits
     `check()` on /connect/ as it is: call `link` through the tool, assert on
     `bay.links()`, call it with an ERR port and assert the refusal text.
  2. **From `demo/verify.mjs` over CDP**: `WebMCP.enable`, read
     `toolsAdded`, `WebMCP.invokeTool`, wait for `toolResponded`. This is the
     way an agent sees the page, so it tests the descriptions and schemas too.
- **The launch needs the feature on.** `demo/verify.mjs` launches without it,
  so a page with tools needs `--enable-features=WebMCP` added for that page
  only, the way `PEER_IN_PAGE` grants audio capture to `wire` and `capture`.
  INFERENCE: one set of slugs, one flag.
- **A negative control is easy and required**: with the feature off,
  `document.modelContext` is `undefined` and the page must register nothing
  and log nothing (MEASURED: the API is absent with no flags).
- **Count the asserts**, as `positron-verify` says: a tools block that
  silently does not register would leave every other assert green.

## 4. Recommendation

**Yes, a small, local first step on /connect/. No shell-wide tool set, no
polyfill, no origin trial token yet.**

1. **In `demo/connect/index.html`**, one block after `redraw()`:
   `const mc = document.modelContext; if (mc) { ... }`, registering
   `list_nodes`, `list_links`, `list_examples` (all `readOnlyHint: true`) and
   `link`, `unlink`, calling the page's own `connect(..., false)` and
   `removeLink`. Every answer carries `{ ok, why, fix }`. One `AbortController`
   so the block can be torn down. About 60 lines (INFERENCE).
2. **In its `check()`**, under `?selfcheck=1` only and only when
   `document.modelContext` exists: execute `link` keys to synth through
   `executeTool` and assert the link exists and the picture shows it; execute
   `link` from `err:station:audio-out` and assert it was refused with the
   *somebody else's server* words; assert `list_links` reads back what
   `bay.links()` holds.
3. **In `demo/verify.mjs`**, `--enable-features=WebMCP` for `connect` only,
   and one CDP pass (`WebMCP.enable`, `invokeTool`) so the route an agent uses
   is graded, not only the in-page one.
4. **Then decide**, with the owner: `build_example`, and whether `play_note`
   and `set_knob` exist while D4 says sound starts on a person's press.
5. **Only after that**, register an origin trial token for positron.studio
   (Chrome 149 to 156) and a separate one for Edge 150, as a `<meta
   http-equiv="origin-trial">` on /connect/ only. INFERENCE: worth it only if
   somebody outside the desk is going to try it before the trial ends.

**What a visitor needs to try it today** (once step 1 is deployed):

- **Chrome 146 or newer** (the API name we use needs 150 or newer; this desk
  has 155), with `chrome://flags/#enable-webmcp-testing` set to Enabled and
  Chrome relaunched. Without our token, the flag is the only way.
- **An agent that consumes it**, one of:
  - the **Model Context Tool Inspector** extension, to see the tools and call
    them by hand, or by sentence with their own Gemini API key;
  - **Claude Code with Chrome DevTools MCP** (`list_webmcp_tools`,
    `execute_webmcp_tool`), pointed at https://positron.studio/connect/;
  - **not** Claude in Chrome (no discovery yet) and **not** Gemini in Chrome
    (announced, not shipped).

**How we would test it**: the in-page and CDP checks in 3.4, run with `node
demo/verify.mjs connect`, plus one look by hand with the inspector extension
on http://127.0.0.1:8890/connect/ in a flagged Chrome.

**What this research did NOT settle:**

- Whether a real (not headless) Chrome lets a tool start an `AudioContext`
  without a gesture. Expected no; not run.
- Whether Claude in Chrome or Gemini in Chrome will pick tools up, and when.
- What happens to the API after Chrome 156.
- ChatGPT Desktop's and Brave Leo's support was read in one line of the CG's
  status page and not tried.
- Edge was not run.

## The probes, for reproducing

In the session scratchpad (`webmcp/`), not in the repository:

- `page.html` and `probe.mjs`: five launches of `launchChrome` from
  `demo/chrome.mjs`, one per flag set, read `window.__probe` and the CDP
  protocol's domain list.
- `proto.mjs`: dumps the `WebMCP` domain from `/json/protocol`.
- `page2.html` and `invoke.mjs`: `WebMCP.invokeTool` on a completing tool, a
  throwing tool, a declarative form and an unknown name; reads
  `navigator.userActivation` inside `execute`.
- Every Chrome they started was closed through `chrome.mjs`'s `close()`;
  `pgrep -fl "Google Chrome.*--headless"` afterwards showed only another
  session's `connect-live` profile, not these.
