# radio1965 — three things measured on their side, 2026-09-15

Follows `radio1965-app-2026-09.md`, which read the app end to end at commit
`0796bf6`. This one is short and is about the running system: what their server
is doing today, what it started doing this week, and two faults worth telling
them about. Same labels as the companion document. **READ** = it is in the
source. **MEASURED** = I asked the running system and this is what it said.

---

## 1. The stream is down, and it is not the port

**MEASURED, twice, 10:33 and 11:12 UTC.** `live.uuu.ee:8001` accepts the TCP
connection and then sends **zero bytes** on every path. Both mounts, same
answer:

| probe | result |
|---|---|
| `nc -z live.uuu.ee 8001` | accepted |
| raw `GET /radio1965 HTTP/1.0` over that socket | 0 bytes back |
| raw `GET /user1 HTTP/1.0` | 0 bytes back |
| `https://live.uuu.ee/radio1965/api/events` | **200**, so the host is up |
| `shout.positron.studio/radio1965` | 502 |

This is the same signature as 2026-09-14, which is already recorded in
CLAUDE.md. Icecast is listening and not answering; the FastAPI server beside it
on the same host is fine.

⚠️ **The control that makes the 502 mean something.** Two other stations go
through the same relay worker on the same deploy, and both answered **200** in
the same second. So the fault is at their end, not ours. A 502 on its own could
not say that, and this project has drawn the wrong conclusion from exactly that
shape before.

⚠️ **And a trap that nearly produced a second wrong conclusion.** `curl` to
port 8001 fails from this sandbox with `000` **and so does a `portquiz.net:8001`
control**, so two failures agree and neither is about their server. The proxy
here refuses non-standard ports; `nc` reaches it. The companion document warns
about this by name and it still nearly landed.

## 2. Their app is showing an on-air banner for a broadcast that ended

**MEASURED.** Two `livestream` events are still `status: new`:

    2026-09-15T00:45:59  livestream  new  http://live.uuu.ee:8001/user1
    2026-09-15T00:44:53  livestream  new  http://live.uuu.ee:8001/radio1965

Both point at mounts that send nothing. **READ** from
`server/icecast_on_disconnect.sh`: that hook is what calls
`POST /events/{id}/unpublish`, and it only runs if Icecast invokes it. An
Icecast that wedges rather than closing a source cleanly never fires it, so the
event stays live for its full `shelf_at` day.

The failure shape is the bad one: the app says a station is on air, somebody
taps it, and nothing plays. It reads as a broken player rather than as a
broadcast that ended. `cron_publish.py`'s time sweep will shelve it eventually,
but a day late.

The fix is theirs to choose, and the cheap one is a liveness check in the
publish cron: an event of type `livestream` whose mount is not in
`status-json.xsl` is not live, whatever the hook did or did not do. That reads
the same registry the on-connect hook already retries against, so it needs no
new machinery.

## 3. Stream recording works, and the files have no CORS

New since the companion document. **READ** at `7366bfe`: a broadcaster sets
`save_stream`, carried in an `ice-audio-info` header; `icecast_on_connect.sh`
starts `ffmpeg -c copy` against the mount; `icecast_on_disconnect.sh` stops it,
rsyncs the mp3 to eccm.ee and calls `finalize-recording`, which turns the
`livestream` event into a `streamrecording` one pointing at an https URL.

**MEASURED** on the one that exists, a 7-second test from 00:34:

| | |
|---|---|
| `https://eccm.ee/radio1965/streams/tester-20260915-003416.mp3` | 200, `audio/mpeg`, LiteSpeed |
| size | 116823 bytes, about 7.3 s at 128 kbit/s |
| a Range request | **206**, `content-range: bytes 0-1/116823` |
| `access-control-allow-origin` | **absent** |
| their events API | `allow-origin: *`, so the JSON is already readable |

So the recordings are on TLS and seekable, and a web page can play one in an
`<audio>` element and read nothing about it. That is the same wall as the live
mount, and it does not affect their own app at all, because Qt is not a browser
and no origin applies. It only matters to anything on the web.

`workers/shout` carries them now at `/rec/<name>.mp3`, matched against the
filename shape their hook writes rather than taking a URL, so it does not become
an open proxy for eccm.ee. Measured through it: 200 with `content-length` and
`accept-ranges`, and `bytes 1000-1999/116823` on a Range.

## What this changes for positron

**A live station has a past now, and it is an ordinary file.** That is the thing
`transport-bar.mjs` refuses to loop over, and the queue item asking for it has
been about recording a window in the browser. Their server already records the
whole broadcast, at the source, losslessly, and publishes it as a seekable mp3
with a start time in the event. A tape of a real broadcast is a different and
better subject than a rolling buffer of the last thirty seconds.

⚠️ **One recording exists and it is seven seconds of a test.** There is nothing
to scrub yet. The pipe is built on their side; the material is not there.
